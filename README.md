# 在庫・発注アラート

商品ごとの在庫数と直近の出荷実績から「いつ・何を・いくつ発注すべきか」を判定するWebアプリ。
解決する課題は4つ — **欠品 / 発注漏れ / 過剰在庫 / 在庫精度（棚卸差異）**。

スプレッドシート＋GAS で運用していたものを、サイト内で完結するように作り直したもの。
マスタ（プルダウンの選択肢）と判定パラメータも画面から編集できるので、スプレッドシートは要らない。

データはこのフォルダの中だけで完結する（外部サービスの契約もDockerも不要）。

```
webapp/                 Next.js（画面・サーバー処理）
webapp/.pglite/         ローカルDBの実体（PostgreSQL本体のWASM版）。初回起動時に作られる
supabase/migrations/    テーブル・判定ビュー・マスタ初期値のSQL
supabase/seed/          動作確認用のサンプル商品（本番では流さない）
在庫・発注アラート_設計書.md    項目定義・計算ロジック・アラート区分
legacy/                 旧スプレッドシート版（GAS・構築プロンプト・使い方ガイド）
```

## 画面

| 画面 | できること |
|:--|:--|
| HOME | 優先度A/B/Cの件数、アラート区分の内訳、要対応リスト（A・B）、在庫金額 |
| 在庫一覧 | 旧シートと同じ42列を横スクロールで一覧。絞り込み・並べ替え・対応状況の変更・CSV書き出し |
| 入出庫 | 入庫・出庫・調整の登録と履歴。入庫元・出荷先の記録、出荷先別の実績、CSV取込・書き出し |
| 商品の追加/編集 | 入力列の編集と、判定の内訳（どの数字がどの式に入って、その区分になったか） |
| 取込・書き出し | 旧シートのCSV取込（移行）、日々の販売データ取込、42列そのままのCSV書き出し |
| 仕入先 | 発注書の宛先。一覧＋「新規登録」。商品編集の候補と入庫元の候補になる |
| 保管場所 | 倉庫・棚番。一覧＋「新規登録」 |
| 出荷先 | 得意先・現場・自社拠点（住所・担当者つき）。一覧＋「新規登録」と、直近の出荷実績 |
| マスタ | 対応状況・カテゴリ・単位の選択肢（旧「マスタ」シート）と、品番の採番ルール |
| 判定パラメータ | 集計期間・安全在庫日数・発注サイクルなど。旧 `CONFIG` にあたる |

## 動かすまで

```bash
cd webapp
npm install
npm run dev        # http://localhost:3000
```

これだけで動く。初回起動時に `webapp/.pglite/` へローカルDB（PostgreSQL本体のWASM版）が作られ、
テーブル・判定ビュー・マスタの初期値まで自動で用意される。

動作確認用のサンプル商品を入れるなら:

```bash
npm run db:seed    # 9件。9つのアラート区分が1件ずつ出るように組んである
npm run db:check   # 判定結果を表で確認する
```

| コマンド | 内容 |
|:--|:--|
| `npm run db:migrate` | テーブル・判定ビュー・マスタ初期値を作る（`npm run dev` でも自動実行される） |
| `npm run db:seed` | サンプル商品9件を入れる |
| `npm run db:check` | 全商品の判定結果を一覧で出す |
| `npm run db:reset` | ローカルDBを消して作り直す（サンプル入り） |

サンプルだけ消すなら `delete from inventory_items where code like 'DEMO-%';`。

> ローカルDBは1プロセスからしか開けない。開発サーバーを動かしたまま `npm run db:*` を実行すると
> 接続できないので、先に開発サーバーを止めること。

### バックアップ

`webapp/.pglite/` フォルダをコピーすれば、それがそのままバックアップになる。
CSVで持ち出す場合は「取込・書き出し」から42列のファイルを書き出す。

### 外部のPostgres（Supabaseなど）へ載せ替えるとき

`webapp/.env.local` に接続先を書くと、ローカルDBの代わりにそちらを使う。SQLは同じものが動く。

```bash
# webapp/.env.local
DATABASE_URL=postgresql://postgres:****@db.xxxxxxxx.supabase.co:5432/postgres
```

テーブルは同じスクリプトで作れる:

```bash
DATABASE_URL="postgresql://..." node scripts/db.mjs migrate
```

Supabase の SQL Editor に `supabase/migrations/` の3ファイルをファイル名順で貼っても同じ。

## 入出庫と出荷先

在庫数を手で書き換える代わりに、入出庫を1件ずつ積み上げられる。

- **入庫 / 出庫 / 調整** を登録すると、理論在庫数がその場で増減する（調整はマイナスも入れられる）
- **出庫には出荷先、入庫には入庫元を記録できる**。出荷先（得意先・現場・自社拠点）は
  「出荷先」ページに住所・担当者つきで登録しておくと、「直近30日でどこへいくつ出たか」を金額つきで集計できる。
  入庫元は仕入先マスタを候補に出しつつ文字列で持つ（他倉庫からの移管や現場からの返却も書けるように）
- 出庫を1件でも登録した商品は、**期間出庫数・最終入出庫日が台帳から自動計算**される。
  登録していない商品は、これまでどおり手入力値・CSV取込値で判定する（移行の途中でも混在してよい）
- 入出庫CSVの見出しは「日付 / 区分 / 商品コード / 数量 / 出荷先 / 入庫元 / 伝票番号 / 備考」。
  必須は先頭4つ。区分は 入庫 / 出庫 / 調整。出荷先は出庫の行、入庫元は入庫の行にだけ書ける
- 取り消し（削除）や数量の修正をすると、理論在庫も同じだけ戻る

商品と入出庫の関係:

```
商品（inventory_items）          入出庫（inventory_movements）
  理論在庫数  ←──── 増減 ────────  入庫 +100 / 出庫 −30 / 調整 −2
  期間出庫数  ←── 直近N日を集計 ──  出庫だけを合計
  最終入出庫日 ←── 最新日を採用 ──  入庫・出庫それぞれの最新
                                      │
                                   出荷先（inventory_destinations）
```

## 品番（商品コードの採番）

商品コードは全処理のキーなので、人によって付け方がばらつくと同じ物に別コードが立ち、
CSV取込でも名寄せできなくなる。マスタ画面で「接頭辞＋連番」のルールを決めておける。

- カテゴリごとにルールを作れる（例: 空調機器→`AC-0001` / 配管部材→`PP-0001`）。
  そのカテゴリ専用のルールが無ければ、カテゴリ空欄の**既定ルール**（`ITEM-0001`）を使う
- 商品の新規登録画面で「採番」を押すと発番される。**押した時点で番号を確保する**ので、
  登録をやめると欠番になる（二人が同時に登録して同じ番号が出るのを防ぐため）
- 既に使われている番号は自動で飛ばす（旧シートから取り込んだコードとぶつかっても止まらない）

## 公開する（Render）

`render.yaml` を同梱してある。Render のダッシュボードで **New → Blueprint** からこのリポジトリを
選ぶと、Webサービスと Postgres がまとめて作られる。

### 1. リポジトリを1つにまとめる

このフォルダ全体（`webapp/` と `supabase/` の両方）が1つのリポジトリに入っている必要がある。
起動時のマイグレーションが `webapp/../supabase/migrations` を読むため、`webapp/` だけを
push するとテーブルが作られない。

```bash
rm -rf webapp/.git          # create-next-app が作った入れ子のリポジトリを外す
git init
git add .
git commit -m "在庫・発注アラート サイト版"
git remote add origin git@github.com:<自分のアカウント>/<リポジトリ名>.git
git push -u origin main
```

### 2. Render で Blueprint を作る

1. [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint**
2. 上のリポジトリを選ぶ → `render.yaml` が読み込まれる
3. **Apply**。Webサービス `inventory-order-alert` と Postgres `inventory-order-alert-db` が作られる

`DATABASE_URL` は Render が自動で繋ぐので、手で入れる必要はない。

### 3. 環境変数を入れる（Environment 画面）

キー | 必須 | 内容
:--|:--:|:--
`BASIC_AUTH_USER` | **必須** | URLを開いたときに聞かれるID
`BASIC_AUTH_PASSWORD` | **必須** | 同パスワード
`NEXT_PUBLIC_APP_URL` | 任意 | 公開URLが決まってから入れる（日次アラート本文のリンク先）
`ALERT_API_TOKEN` | 自動 | Render が自動生成する。cron から叩くときに使う
`RESEND_API_KEY` / `ALERT_MAIL_TO` / `ALERT_MAIL_FROM` | 任意 | 日次アラートをメールで送るとき

**このアプリには画面内のログインが無い。** Basic認証を空のままにすると、URLを知っている人は
誰でも在庫・仕入先・出荷先を見られる。必ず入れること。

### 4. 初回デプロイ

デプロイのたびに `npm run start:deploy`（= マイグレーション → 起動）が走る。
テーブル・判定ビュー・マスタ初期値は自動で用意されるので、SQLを手で流す必要はない。

`https://<サービス名>.onrender.com` が公開URL。Basic認証のダイアログが出れば成功。

### 5. サンプルデータを入れる（見せる用・任意）

Environment に `SEED_SAMPLE_DATA=true` を足して保存すると、次のデプロイで動作確認用の
商品10件と入出庫6件が入る（9つのアラート区分が1件ずつ出るように組んだもの）。
何度デプロイしても増えない。実データを入れる前のデモに使う。

消すときは、環境変数を外したうえで画面から商品を削除するか、SQLで:

```sql
delete from inventory_movements m using inventory_items i
 where m.item_id = i.id and i.code like 'DEMO-%';
delete from inventory_items where code like 'DEMO-%';
```

### 6. 実データを移す

`SEED_SAMPLE_DATA` を入れなければ商品は0件で立ち上がる。手元のデータを移すなら:

1. ローカルの「取込・書き出し」→ 全商品をCSVで書き出す／入出庫をCSVで書き出す
2. 公開先の「取込・書き出し」で、商品CSV → 入出庫CSV の順に取り込む

### 7. 日次アラートを自動で送る（任意）

Render の **New → Cron Job** で、毎朝この1行を実行する。

```bash
curl -fsS "https://<サービス名>.onrender.com/api/alerts/daily?token=$ALERT_API_TOKEN&send=1"
```

### 気をつける点

- **無料プランはスリープする。** 15分アクセスが無いと停止し、次に開くとき30秒ほどかかる。
  `.github/workflows/keep-awake.yml` が10分おきに `/api/healthz` を叩いて起こし続けている
  （止めるときはこのファイルを消すか、GitHub の Actions タブで Disable）。
  ただし Render の無料枠は**アカウント全体で月750時間**なので、24時間起こし続けると
  1サービスでほぼ使い切る。他にも無料サービスを動かしているなら、業務時間だけに絞ること
- **無料Postgresには期限・容量の制限がある。** 実運用に載せる前に、現在のプラン条件を
  Render のダッシュボードで確認すること（期限切れでDBごと消える設定になっていないか）
- **ローカルDB（`webapp/.pglite/`）は公開先では使わない。** Render のファイルは再デプロイで
  消えるため。`DATABASE_URL` が入っていれば自動的に Postgres を見る
- リージョンはWebサービスとDBを必ず揃える（別リージョンだと内部接続が使えず遅くなる）

## 旧スプレッドシートからの移行

1. 旧シートを開き、ファイル → ダウンロード → **カンマ区切り形式(.csv)**
2. アプリの「取込・書き出し」でそのファイルを指定 → 内容を確認 → 取り込む

見出しの並びは旧シートのままでよい。自動計算列（有効在庫・発注点・アラート区分など）は読み飛ばす。
商品コードが一致する行は更新、無ければ新規追加。**CSVに載っていない列は今の値のまま残る**ので、
「商品コード＋期間出庫数」だけのファイルを毎日流し込む運用もできる。

## 日次アラート（旧 `sendAlertMail` + 毎朝8時トリガー）

`GET /api/alerts/daily?token=...` が優先度A・Bの一覧を返す。`&send=1` を付けるとメールを送る
（`RESEND_API_KEY` / `ALERT_MAIL_TO` / `ALERT_MAIL_FROM` が揃っているときだけ）。

`ALERT_API_TOKEN` を設定しない限り、この入口は 503 を返して動かない。
cron（Vercel Cron・Render Cron・GitHub Actions など）から毎朝叩く想定。

## 設計上の要点

- **判定は保存しない。** 有効在庫・発注点・アラート区分などは `inventory_items_evaluated`
  ビューが毎回その場で計算する。だから「再計算ボタン」が無く、在庫数を直せば判定はその瞬間に変わる。
  保存していた旧版は、日付が変わると前日の判定が残ったままになっていた。
- **発注判定は「有効在庫＋発注残」で行う。** 有効在庫だけで見ると、発注済みの商品に毎日
  同じアラートが出続けて誰も見なくなる。
- **対応状況は人の列。** 機械はアラートを出すだけで、対応状況（発注済み・保留・廃盤 など）は
  人が決める。計算がこの列を書き換えることはない。
- **入出庫は残高を動かす。** 台帳の合計を毎回数え直すのではなく、理論在庫数という残高を
  トリガーが増減させる。過去分を後からCSVで入れても「今の残数」が壊れないようにするため。
- **台帳が無くても動く。** 出庫を登録していない商品は、これまでどおり手入力の期間出庫数で判定する。
  全商品の入出庫を揃えなくても、入れたものから順に精度が上がる。
- **ログインは無い。** DBアクセスは全てサーバー側で行い、ブラウザからDBへは一切つながらない。
  社外から触れる場所へ公開するときは、置き場所側（Basic認証・IP制限など）で入口を塞ぐこと。
- **ローカルDBも本物のPostgres。** PGlite（PostgreSQL 17 をWASMにしたもの）なので、
  判定ビューのSQLはそのまま Supabase や自前のPostgresでも動く。移行時に書き直す箇所は無い。
