## §1 コピペ用プロンプト

````text
Googleスプレッドシートで「在庫・発注アラート」システムを構築してください。

## 対象
- スプレッドシート: {{スプレッドシートURL}}
- シート名: {{在庫・発注アラート}}
- 業種・取扱品: {{空調設備の卸・工事業／エアコン本体、配管部材、消耗品}}

## ゴール
商品ごとの在庫数と直近の出荷実績から「いつ・何を・いくつ発注すべきか」を
毎朝自動で判定する。解決する課題は4つ:
欠品 / 発注漏れ / 過剰在庫 / 在庫精度（棚卸差異）。

## 成果物
1. スプレッドシート本体（見出し・サンプルデータ・数式・書式・プルダウン）
2. Google Apps Script `在庫アラート.gs`（再計算・メール通知・日次トリガー）
3. 設計書 Markdown（項目定義・計算ロジック・アラート区分）
4. 使い方ガイド PDF（図解入り・A4）

## 1. 列構成（全42列 / A〜AP）

区分ごとに並べる。この並び順がそのまま列番号になる。

| # | 列 | 項目 | 入力/自動 | 備考 |
|--:|:--|:--|:--:|:--|
| 1 | A | 対応状況 | **人** | プルダウン。保護列 |
| 2-7 | B-G | 商品コード / 商品名 / カテゴリ / 規格・型番 / 単位 / 保管場所 | 入力 | 商品コードは重複禁止 |
| 8-14 | H-N | 仕入先コード / 仕入先名 / 仕入単価 / 販売単価 / 発注リードタイム日数 / 最小発注数(MOQ) / 発注ロット単位 | 入力 | リードタイムが発注点計算の中核 |
| 15-22 | O-V | 理論在庫数 / 実棚在庫数 / 棚卸差異 / 引当数(受注残) / 発注残数(入荷予定) / 有効在庫数 / 入荷予定日 / 在庫金額 | 混在 | 棚卸差異・有効在庫数・在庫金額は自動 |

| 27-32 | AA-AF | 安全在庫日数 / 安全在庫数 / 発注点 / 適正在庫上限 / 発注推奨数 / 発注期限日 | 混在 | 安全在庫日数のみ入力 |
| 33-36 | AG-AJ | アラート区分 / 優先度 / アラート理由 / 推奨アクション | 自動 | アラート区分は**数式**、他はGAS |
| 37-42 | AK-AP | 最終入庫日 / 最終出庫日 / 最終棚卸日 / 滞留日数 / 備考 / 更新日時 | 混在 | 滞留日数・更新日時は自動 |

## 2. 計算ロジック

```
有効在庫     = (実棚在庫があれば実棚 / 無ければ理論在庫) − 引当数
在庫ポジション = 有効在庫 + 発注残数        ← 発注判定はこの値で行う
平均日次出庫  = 期間出庫数 ÷ 30
在庫日数     = 有効在庫 ÷ 平均日次出庫
欠品予測日    = 今日 + 在庫日数
安全在庫     = 平均日次出庫 × 安全在庫日数(既定7)
発注点       = 平均日次出庫 × リードタイム + 安全在庫
適正在庫上限  = 平均日次出庫 × (リードタイム + 安全在庫日数 + 発注サイクル14)
発注推奨数    = ceil( max(適正在庫上限 − 在庫ポジション, MOQ) ÷ ロット ) × ロット
発注期限日    = 欠品予測日 − リードタイム
滞留日数     = 今日 − 最終出庫日
```

**最重要**: 発注判定を「有効在庫」ではなく「**有効在庫＋発注残**」で行うこと。
これをしないと、発注済みの商品に毎日重複アラートが出続けて誰も見なくなる。

## 3. アラート区分（上から順に評価し、最初に該当した1つだけを採用）

| # | 区分 | 条件 | 優先度 |
|--:|:--|:--|:--:|
| 1 | 欠品 | 有効在庫 ≦ 0 | A:即日対応 |
| 2 | 発注漏れ | 発注点割れ かつ 発注残0 かつ 発注期限日を超過 | A:即日対応 |
| 3 | 欠品リスク | 在庫日数 ≦ リードタイム | A:即日対応 |
| 4 | 入荷遅延 | 入荷予定日 < 今日 かつ 発注残 > 0 | B:3日以内 |
| 5 | 発注推奨 | 在庫ポジション ≦ 発注点 | B:3日以内 |
| 6 | 過剰在庫 | 有効在庫 > 適正在庫上限 | C:要確認 |
| 7 | 滞留在庫 | 90日以上 出庫なし かつ 在庫あり | C:要確認 |
| 8 | 棚卸差異 | 実棚 ≠ 理論 | C:要確認 |
| — | 正常 | どれにも該当しない | - |

アラート理由には判定根拠の数値を、推奨アクションには次に取る行動を
仕入先名・数量入りの日本語文で自動生成すること。

## 4. アラート区分列（AG）は ARRAYFORMULA で実装

AG2 に1本だけ入れ、以降の行は自動展開させる。GASの値書き込みにしない。
理由: 在庫数を手で直した瞬間に判定が変わってほしいため。

実装時の必須事項:
- `IFS` を使い、上記の優先順位どおりに条件を並べる（最初に真のものが返る）
- **空欄ガードを各条件に入れる**。Sheetsでは空セルの日付は 1899/12/30 扱いになるため、
  `(U2:U<>"")*(U2:U<TODAY())` のようにしないと未入力行が全部「入荷遅延」になる
- **`AND()` は使わない**。ARRAYFORMULA 内で配列に展開されないため、条件の連結は `*` で行う
- 末尾に `TRUE, "正常"` を置く。IFS はどれにも該当しないと #N/A を返す
- 全体を `IF(B2:B="","", ...)` で囲み、空行を空欄のままにする

## 5. Apps Script `在庫アラート.gs`

### 構成
- `CONFIG` — 調整パラメータ（冒頭にまとめる）
  `DEMAND_WINDOW_DAYS:30` / `DEFAULT_SAFETY_DAYS:7` / `ORDER_CYCLE_DAYS:14`
  `DEAD_STOCK_DAYS:90` / `COUNT_DIFF_TOLERANCE:0` / `NO_MOVE_DAYS:9999`
- `HEADERS` — 42項目の配列
- `C` — 列番号の定数（1始まり）。HEADERS の並びと必ず一致させる
- `INPUT_COLS` — 人／CSVが埋める列
- `PROTECTED_COLS` — 再計算が絶対に触らない列
- `onOpen()` — カスタムメニュー「在庫アラート」を追加
- `setupHeaders()` — 見出し・色分け・表示形式・プルダウン・マスタシートを一括生成
- `recalcAll()` → `evaluateRow_()` — 全行の自動列を再計算
- `sendAlertMail()` — 優先度A・Bを1通にまとめて送信
- `createDailyTrigger()` / `dailyJob()` — 毎朝8時に再計算＋通知

### 絶対に守ること

**(a) 保護列を書き戻さない**
```js
const PROTECTED_COLS = [C.STATUS, C.ALERT];  // A列(人の判断) と AG列(数式)
```
`sheet.getRange(2,1,n,HEADERS.length).setValues(out)` のような**行まるごとの書き込みは禁止**。
保護列を飛ばし、連続する範囲ごとに分割して setValues すること。
（この例では B〜AF と AH〜AP の2ブロックになる）

**(b) `setConditionalFormatRules` は既存ルールを全置換する**
条件付き書式をGAS側に集約し、シートで手動設定したものも含めて全部そこで再現すること。
一部だけ設定すると、実行のたびに他のルールが消える。

**(c) 列番号はハードコードせず `C.XXX` 経由で参照する**
行赤塗りのカスタム数式なども `sheet.getRange(2, C.ALERT).getA1Notation()` から組み立て、
列が増減しても追従するようにする。

**(d) マスタシートは既存なら中身に触らない**
`ensureMasterSheet_()` は無いときだけ作る。運用中に追加された選択肢を消さないため。

## 6. プルダウン（「マスタ」シートで一元管理）

マスタシートの各列に選択肢を置き、`ONE_OF_RANGE` で `マスタ!$A$2:$A` のように
**開放範囲**で参照する。行を足すだけで全行に反映されるようにする。

| マスタ列 | 対象列 | 選択肢 | 入力制限 |
|:--|:--|:--|:--|
| A | A 対応状況 | 即日対応 / 要確認 / 発注済み / 保留 / 廃盤 / 発注NG | **あり**（リスト外を弾く） |
| B | D カテゴリ | 業種に合わせて7個程度 | なし（警告のみ） |
| C | F 単位 | 台 / 箱 / 本 / 個 / 枚 / 巻 / m / kg / 式 / セット / ケース | なし |
| D | G 保管場所 | 倉庫・棚番 | なし |
| E | I 仕入先名 | 取引先名 | なし |

対応状況だけ制限をかけるのは、人が絞り込みに使う列で表記ゆれが致命的になるため。
残り4列を警告止まりにするのは、CSV取込で新しい値が来たときに取込自体を失敗させないため。

アラート区分・優先度にはプルダウンを付けない（自動生成列なので「無効な値」警告だらけになる）。

---

## 7. 書式

- 1行目: 太字・中央・折り返し・区分ごとに背景色。行固定
- 列固定: 3列（対応状況・商品コード・商品名）
- 単価と在庫金額 `¥#,##0` / 日付 `yyyy/mm/dd` / 更新日時 `yyyy/mm/dd hh:mm`
- 平均日次出庫数 `0.00` / 在庫日数・安全在庫数・発注点・適正在庫上限 `0.0`
- 条件付き書式:
  - A列 対応状況: 6値それぞれに色（即日対応=赤 / 要確認=黄 / 発注済み=緑 / 保留=灰 / 廃盤=濃灰 / 発注NG=紫）
  - AG列 アラート区分: 8区分＋正常にそれぞれ色
  - AH列 優先度: **前方一致**で A=赤 / B=黄 / C=青（値が `A:即日対応` 形式のため完全一致だと外れる）
  - **「発注漏れ」の行は A〜AP 全体を薄赤に**（カスタム数式 `=$AG2="発注漏れ"`）

---

## 8. サンプルデータ（2〜5行目）

**4行それぞれで別のアラート区分が出るように**入力値を設計すること。
最低限、優先度A・B・Cが揃うようにする。推奨の組み合わせ:

| 行 | 狙う区分 | 作り方 |
|:--|:--|:--|
| 2 | 発注漏れ(A) | 発注点割れ・発注残0・発注期限を過ぎた状態にする |
| 3 | 入荷遅延(B) | 発注残を持たせ、入荷予定日を過去にする。在庫日数 > リードタイム にして欠品リスクを回避 |
| 4 | 過剰在庫(C) | 在庫日数が3桁になるまで在庫を積む |
| 5 | 棚卸差異(C) | 理論と実棚をずらす。発注も過剰も出ない水準に置く |

自動列は上記の計算ロジックどおりに算出した値を入れること（手書きの適当な値を入れない）。
GASを実行したとき同じ値になるかで実装の正しさを検証できる。

---

## 9. 検証（実装後に必ず実行）

1. `HEADERS.length` と `C` の定義数が一致し、全項目で `HEADERS[C[key]-1]` が正しい列名を指すか
2. 保護列を除いた書き戻し範囲に**書き漏れ0件・保護列への誤書き込み0件**か
3. AG列の数式出力が、手計算したサンプル4行の区分と一致するか
4. `node --check` 等で .gs の構文エラーがないか

---

## 10. 禁止事項

- **列の挿入・削除をしない**。どうしても必要なら末尾に追加し、`HEADERS` と `C` を同時に直す
  （途中に1列挿すだけで全定数がズレ、再計算でデータが壊れる）
- 自動列に手入力しない
- AG3以降に値を入れない（ARRAYFORMULA が #REF! になる）

## 11. ドキュメント

設計書（Markdown）と使い方ガイド（PDF）を作る。
PDFは HTML + インラインSVG を書き、ヘッドレスChromeで印刷する:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --no-pdf-header-footer \
  --print-to-pdf="使い方.pdf" "file://$(pwd)/使い方.html"
```

図は最低5点:
1. 全体フロー（入力→計算→判定→通知→対応。人が触る範囲を明示）
2. 列構成マップ（区分ごとの帯。保護列を明示）
3. **在庫推移グラフ**（のこぎり波＋発注点・安全在庫・適正上限の3本線＋リードタイム区間＋
   「発注しないとここで欠品」の破線）← これが一番重要
4. アラート判定の順序（条件→区分→優先度の梯子型）
5. 対応状況の遷移（即日対応→発注済み→解消／保留・廃盤・発注NG）
````

## §3 パラメータの意味（発注量と在庫量のトレードオフ）

| パラメータ | 既定 | 大きくすると | 小さくすると |
|:--|--:|:--|:--|
| `DEMAND_WINDOW_DAYS` | 30 | 判定が安定するが需要変化に鈍くなる | 季節変動に追従するがブレやすい |
| `DEFAULT_SAFETY_DAYS` | 7 | 欠品しにくいが在庫が増える | 在庫は減るが欠品リスクが上がる |
| `ORDER_CYCLE_DAYS` | 14 | 発注回数が減るが1回の量と在庫が増える | こまめな発注になり事務負荷が上がる |
| `DEAD_STOCK_DAYS` | 90 | 滞留の警告が出にくい | 季節商品が滞留扱いされやすい |

## §4 この指示が必要な理由（実装時に踏んだ落とし穴）

| 指示 | 入れないとどうなるか |
|:--|:--|
| 判定は「有効在庫＋発注残」 | 発注済みの商品に毎日アラートが出続け、誰も見なくなる |
| ARRAYFORMULA の空欄ガード | 空セルの日付が 1899/12/30 扱いになり、未入力行が全部「入荷遅延」になる |
| `AND()` ではなく `*` | ARRAYFORMULA 内で AND が配列展開されず、全行が同じ結果になる |
| IFS の末尾に `TRUE` | どれにも該当しない行が #N/A になる |
| `PROTECTED_COLS` | 再計算1回で、手入力の対応状況とAG列の数式が値に潰れる |
| 条件付き書式をGASに集約 | `setConditionalFormatRules` が全置換なので、実行のたびに他のルールが消える |
| 優先度は前方一致で判定 | 値が `A:即日対応` 形式のため、完全一致 `"A"` だと色が付かずメール抽出も0件になる |
| 列の挿入禁止 | 列番号定数が全部ズレ、再計算でデータが破壊される |
